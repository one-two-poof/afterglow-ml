# 현행 코스 추천 로직과 장소 데이터 계약

작성 기준: 2026-09-09 현재 저장소의 실제 실행 코드

## 1. 문서 목적과 기준

이 문서는 대량의 장소 데이터를 현행 추천 엔진에 넣기 전에 반드시 맞춰야 하는 데이터 계약과, 엔진이 코스를 만드는 실제 규칙을 설명한다.

설명의 기준은 과거 설계 문서가 아니라 다음 실행 경로다.

```text
POST /api/course
  -> app.service.inference.apply_rule
  -> category / activity_level / distance / treatment 규칙
  -> app.service.course.generate_courses
  -> 추천 결과 DB 저장
```

`mdfile/RULE_LOGIC_GUIDE.md`와 일부 테스트는 삭제된 과거 모듈과 점수 체계를 설명한다. 특히 100점 만점 Place Score, 모든 3개 장소 조합 탐색, Course Score 재정렬은 현행 코드에 없다. 데이터 정제와 로직 수정은 이 문서를 기준으로 하되, 최종 판단은 항상 실행 코드로 확인해야 한다.

## 2. 한눈에 보는 현재 추천 방식

```text
DB의 attractions 전체 로드
  -> 목적 키워드 점수(+8, 최대 1회)
  -> 활동 난이도 점수(-5 ~ +3)
  -> 날짜별 출발점 결정
  -> 출발점 반경 밖 장소 제거 + 거리 점수(+2 ~ +10)
  -> 해당 날짜의 시술 위험 장소 차단 또는 감점(-5, 최대 1회)
  -> 하루 3개 장소 × 3개 코스를 MMR 방식으로 순차 선택
  -> 선택된 3개 장소의 방문 순서를 거리와 슬롯 힌트로 재배열
  -> 여행의 같은 순위끼리 날짜별 일정을 묶어 3개 추천 결과 반환
  -> DB 저장 후 생성 ID를 course_id로 반환
```

중요한 성질은 다음과 같다.

- ML 모델은 호출되지 않는다. 현재 `/api/course`는 전부 규칙 기반이다.
- 후보 장소는 요청마다 `attractions` 테이블 전체를 메모리에 읽는다.
- 하루 일정은 반드시 장소 3개이며, 하루에 코스 3개를 만들려면 최소 9개의 서로 다른 유효 장소가 필요하다.
- 한 요청 안에서는 날짜와 순위를 가리지 않고 같은 장소를 다시 쓰지 않는다.
- 코스의 `rank`는 최종 코스 점수 순위가 아니라 1번부터 탐욕적으로 만든 순서다.

## 3. 요청과 날짜별 처리

요청의 핵심 필드는 다음과 같다.

| 필드 | 규칙에서의 역할 |
|---|---|
| `trip_start_date`, `trip_end_date` | 양 끝 날짜를 포함해 하루씩 순회한다. |
| `user_purpose` | `문화관광`, `뷰티쇼핑`, `휴식` 중 하나이며 목적 키워드와 슬롯 설정을 고른다. |
| `mobility_range` | 1~5. 출발점 반경, 장소 간 거리 점수, 슬롯 근거리 풀 범위를 결정한다. |
| `activity_level` | 1~5. 각 장소의 `walk_hard`와 차이를 점수화한다. |
| `daily_startList` | 여행의 모든 날짜에 정확히 대응하는 출발점이 필요하다. 코드상 중복 날짜는 첫 항목만 사용한다. |
| `treatmentList` | 시술명과 날짜를 받아 각 여행 날짜에 BLOCK/PENALTY를 적용한다. |

출발점의 `place_type`이 `ATTRACTION`이면 `attractions.id`, 그 외 `HOSPITAL` 또는 `ACCOMMODATION`이면 `hospitals_accommodations.id`를 조회한다. 타입과 실제 DB 행의 `primary_type`이 일치하는지는 검사하지 않는다.

시작일이 종료일보다 늦어도 요청 스키마에서 막지 않는다. 이 경우 날짜 루프가 비어 최종 추천도 빈 배열이 될 수 있다. `daily_startList`의 날짜 완전성·중복과 시술일 범위도 스키마 단계에서는 교차 검증하지 않는다.

## 4. 추천 엔진이 실제로 소비하는 장소 필드

`attractions` 테이블에서 규칙 결과에 직접 영향을 주는 필드는 아래뿐이다.

| DB 필드 | CSV 관례 | 내부 사용 | 필수 조건/권장값 |
|---|---|---|---|
| `id` | CSV에는 보통 없음 | 추천 내부 식별자, 출발 관광지 조회, 중복 방지 | DB 적재 시 유일한 정수 PK 필요 |
| `place_name` | `placeName` | 응답 표시 | 비어 있으면 안 됨 |
| `primary_type_name` | `primaryTypeName` | `place_category`; 목적 매칭, 다양성, 드럭스토어 제한, 목적별 제외 | 정규화된 고정 표시값 권장 |
| `category_name` | `categoryName` | 상세 키워드 매칭과 상세 카테고리 중복 벌점 | 원본의 충분한 카테고리 경로 보존 |
| `map_x` | `mapX` | 경도(longitude) 원본 | 유효 숫자 필수 |
| `map_y` | `mapY` | 위도(latitude) 원본 | 유효 숫자 필수 |
| `is_indoor` | `isIndoor` | 0이면 야외 노출로 판정 | 0/1 또는 boolean, 결측 금지 권장 |
| `is_heat_source` | `isHeatSource` | 열 노출 위험 판정 | 0/1 또는 boolean, 결측 금지 권장 |
| `is_massage_spot` | `isMassageSpot` | 압박/마사지 위험 판정 | 0/1 또는 boolean, 결측 금지 권장 |
| `walk_hard` | `walkHard` | 활동 점수 및 4 이상일 때 고활동 판정 | 정수 1~5 |

다음 필드는 DB에는 저장되지만 현재 추천 점수·필터·응답에는 쓰이지 않는다.

- `place_id`/`kakaoPlaceId`
- `primary_type`/`primaryType`
- `collection_types`/`collectionTypes`
- `category_group_code`, `category_group_name`
- `phone`, 주소, `place_url`
- CSV의 `popularity`, `isNa`, `skinTreatmentConfidence`, `skinTreatmentSignals`

단, 이 값들은 수집 품질 관리와 재적재 시 식별에 필요하므로 삭제할 필드는 아니다. 특히 `kakaoPlaceId`는 대량 병합 중 중복 제거의 안정적인 키다.

### 좌표 주의사항

원본과 DB는 `mapX=경도`, `mapY=위도`다. 추론 내부에서는 하버사인 함수에 맞추기 위해 다음처럼 이름을 바꿔 담는다.

```text
내부 mapX = DB map_y = 위도
내부 mapY = DB map_x = 경도
```

응답 스키마의 `mapX`, `mapY` 설명은 각각 위도와 경도로 되어 있어 원본 CSV 관례와 반대다. 대량 정제 과정에서는 원본/DB 좌표를 뒤집으면 안 된다.

결측 좌표는 현재 코드가 오류로 막지 않고 `0.0`으로 바꾼다. 서울 기준으로는 거리 필터에서 대개 제거되지만, 데이터 오류가 조용히 숨겨지므로 적재 전에 반드시 거부해야 한다.

## 5. 장소의 기본 점수

한 요청에서 모든 장소는 먼저 0점으로 시작한다. 목적 점수와 활동 점수는 날짜와 무관하게 한 번 적용하고, 거리와 시술 규칙은 날짜별 복사본에 적용한다.

```text
raw_score
= 목적 키워드 점수
+= 활동 난이도 점수
+= 해당 날짜 출발점 거리 점수
+= 해당 날짜 시술 감점
```

### 5.1 목적 키워드 점수

`primaryTypeName + categoryName` 문자열에 목적별 키워드가 하나라도 부분 일치하면 `+8`이다. 여러 키워드가 일치해도 한 번만 더한다.

- 문화관광: 미술관, 전시, 공연, 박물관, 문화원, 영화관, 복합문화공간, 테마거리, 유적지 등
- 뷰티쇼핑: 드럭스토어, 올리브영, 백화점, 화장품, 패션, 쇼핑, 상설시장 등
- 휴식: 카페, 공원, 숲, 산, 산책, 정원, 스파, 찜질방, 사우나, 마사지 등

정확한 목록은 `app/config/rule_config.yaml`의 `category_rule.purpose_keywords`가 단일 실행 기준이다.

다음 테마형 장소 문자열이 포함되면 목적 매칭과 슬롯 매칭에서 모두 제외되고, 코스 선택 단계에서도 완전히 제외된다.

```text
보드카페, 만화카페, 키즈카페, 이스케이프, 방탈출, 벌툰, 스키(보드), 렌탈샵
```

### 5.2 활동 난이도 점수

`abs(activity_level - walk_hard)`로 계산한다.

| 차이 | 점수 |
|---:|---:|
| 0 | +3.0 |
| 1 | +1.5 |
| 2 | 0.0 |
| 3 | -3.0 |
| 4 | -5.0 |

사용자 활동 수준보다 쉬운 장소도 차이만큼 감점될 수 있다. 예를 들어 `activity_level=5`, `walk_hard=1`은 -5점이다.

## 6. 거리 규칙

거리는 지구 반지름 6,371km의 Haversine 직선거리이며 계산 즉시 소수 셋째 자리로 반올림한다. 실제 도보 경로나 소요 시간이 아니다.

날짜별 출발점에서 최대 허용 거리보다 멀면 후보에서 제거한다.

| mobility | 최대 반경 | 거리 구간별 가점(가까운 순) |
|---:|---:|---|
| 1 | 1.0km | ≤0.07:+10, ≤0.2:+9, ≤0.4:+7, ≤0.7:+4, ≤1.0:+2 |
| 2 | 3.0km | ≤0.2:+10, ≤0.6:+9, ≤1.2:+7.5, ≤2.1:+5.5, ≤3.0:+3 |
| 3 | 5.0km | ≤0.4:+10, ≤1.0:+9, ≤2.1:+7.5, ≤3.8:+5.5, ≤5.0:+3 |
| 4 | 7.0km | ≤0.7:+10, ≤1.6:+9, ≤3.1:+7.5, ≤5.3:+5.5, ≤7.0:+3 |
| 5 | 9.0km | ≤0.9:+10, ≤2.3:+9, ≤4.5:+7.5, ≤6.8:+5.5, ≤9.0:+3 |

두 번째·세 번째 장소를 고를 때는 직전 선택 장소와의 거리에도 같은 표의 점수를 추가한다. 최대 허용 거리 밖이면 해당 선택 단계에서 제외한다.

## 7. 시술 안전 규칙

장소 위험 신호는 데이터 필드로 결정한다.

| 위험 신호 | 판정 |
|---|---|
| `high_activity` | `walkHard >= 4` |
| `outdoor_exposure` | `isIndoor == 0` |
| `heat_exposure` | `isHeatSource == 1` |
| `massage_pressure` | `isMassageSpot == 1` |

시술일 당일은 0일 차다. 여행 날짜가 시술일보다 이르면 해당 시술은 무시한다. `elapsed_days <= max_day`인 동안 규칙이 적용되며, 음수가 아닌 일수에 별도 상한은 없다.

| 시술 | 고활동 | 야외 | 열 | 마사지/압박 |
|---|---|---|---|---|
| 리프팅 | 0~2일 감점 | 0~7일 감점 | 0~7일 차단 | 0~7일 감점 |
| 보톡스 | 0일 차단, 1~7일 감점 | 없음 | 0~7일 차단 | 0~7일 차단 |
| 필러 | 0~7일 감점 | 없음 | 0~7일 차단 | 0~7일 차단 |
| 스킨부스터 | 0~7일 감점 | 0~2일 차단, 3~7일 감점 | 0~7일 차단 | 0~7일 감점 |
| 윤곽/체형주사 | 0~7일 감점 | 없음 | 0~7일 차단 | 0~7일 감점 |
| 필링 | 0~7일 차단 | 0~7일 차단 | 0~7일 차단 | 0~3일 감점 |
| 피부레이저 | 0~3일 감점 | 0~7일 차단 | 0~7일 차단 | 0~3일 감점 |
| 피부관리 | 없음 | 없음 | 0~7일 감점 | 없음 |
| 제모 | 없음 | 0~7일 차단 | 0~7일 차단 | 없음 |
| 비만(약처방) | 없음 | 없음 | 없음 | 없음 |

하나라도 BLOCK이면 장소를 즉시 제거한다. PENALTY가 여러 위험 신호 또는 여러 시술에서 발생해도 장소 전체 감점은 `-5` 한 번뿐이다. 어떤 규칙이 맞았는지는 응답에 노출되지 않는다.

## 8. 하루 3개 코스를 만드는 방법

### 8.1 전역 중복 제거

`generate_courses`는 하루에 rank 1부터 3까지 순서대로 만든다. 이미 이 요청의 이전 날짜 또는 당일 앞선 코스에서 사용된 장소 ID는 전부 제외한다. 따라서 다음이 성립한다.

```text
같은 하루의 세 코스: 장소 완전 비중복
서로 다른 날짜: 장소 완전 비중복
```

코스 하나는 서로 다른 장소 3개와 최소 2개의 서로 다른 `primaryTypeName`이 필요하다. 하루 3개가 모두 생성되지 않으면 요청 전체가 400 오류로 끝나고 저장도 롤백된다.

### 8.2 후보 적합도와 MMR

각 슬롯에서 후보의 원점수는 다음과 같다.

```text
후보 원점수 = 누적 장소 점수
             + 직전 장소 거리 점수(2·3번째 장소)
             + 현재 슬롯 키워드 보너스
             + 첫 슬롯 쇼핑 페널티(문화관광/휴식만 -0.8)
```

선택 풀 안의 원점수를 0~1로 min-max 정규화한 뒤 아래 MMR 값을 최대화한다.

```text
MMR = 0.65 * 정규화 적합도
    + 1.2 * 코스 내부 근접도
    - 0.35 * 1.2 * (0.7 * 카테고리 유사도 + 0.4 * 타 코스 근접도)
```

- 같은 `categoryName`: 카테고리 유사도 1.0
- 같은 `primaryTypeName`: 카테고리 유사도 0.55
- 코스 내부 근접도: 직전 선택 장소에서 0.3km 이하면 1, 1.0km 이상이면 0, 사이는 선형 보간
- 타 코스 근접도: 당일 먼저 만든 코스 장소에서 0.15km 이하면 1, 0.6km 이상이면 0, 사이는 선형 보간

첫 장소는 코스 내부 근접도가 0이다. 모든 후보의 원점수가 같으면 정규화 적합도를 모두 1로 처리한다.

### 8.3 후보 풀의 우선순위

기본적으로 각 슬롯은 다음 풀에서 처음 선택 가능한 결과를 사용한다.

1. 목적 전체 키워드에 맞고, 직전 장소(첫 슬롯은 출발점)에서 `slot_max_hop` 안이며, 아직 코스에 없는 대분류
2. `slot_max_hop` 안이며, 아직 코스에 없는 대분류
3. 아직 코스에 없는 대분류
4. 전체 유효 후보

`slot_max_hop`은 mobility 1~5에 각각 1.8, 2.5, 3.5, 4.0, 5.0km다. 이는 하드 제한이 아니라 앞선 후보 풀을 만드는 기준이다. 풀이 비면 더 먼 후보나 같은 대분류 후보로 폴백한다.

슬롯 키워드는 하드 조건이 아니라 +1(1·2번 슬롯) 또는 +1.5(3번 슬롯)의 힌트다. 또한 풀 1의 “목적 키워드”는 해당 슬롯 키워드만이 아니라 그 목적의 세 슬롯 키워드를 합친 목록이다.

`뷰티쇼핑.skip_categories`는 `primaryTypeName`과 정확히 일치할 때만 제외한다. 설정값은 `마사지/경락/안마`, `스파`, `찜질방/사우나`, `이색찜질방`인데 현재 수집기는 마사지·스파를 `안마/스파`로 정규화하므로 그 행들은 이 설정으로 제외되지 않는다. 다만 시술 위험 규칙은 별도로 계속 적용된다.

### 8.4 방문 순서 재배열

MMR로 고른 세 장소는 선택 순서를 그대로 쓰지 않고 다시 정렬한다.

- 출발점에서 시작해 `거리(km) - 슬롯 보너스`가 가장 작은 장소를 다음 장소로 고른다.
- 가능하면 직전 장소와 같은 `primaryTypeName`이 연속하지 않게 한다.
- 마지막 장소에서 출발점으로 돌아오는 거리는 계산하지 않는다.
- 응답의 `dist_to_prev_km`는 각 구간을 소수 둘째 자리로 반올림한 값이다.

재배열 단계에는 `slot_max_hop`이나 전체 이동 거리 상한이 없다. 따라서 선택 단계에서 허용된 장소들이 재배열된 뒤에는 인접 구간이 mobility 최대 거리보다 길어질 가능성이 있다.

## 9. 순위와 응답 저장

각 날짜의 첫 번째 생성 코스끼리 rank 1, 두 번째끼리 rank 2, 세 번째끼리 rank 3으로 묶는다. 여러 날의 `total_distance_km`는 각 장소의 반올림된 `dist_to_prev_km`를 모두 합산하고 마지막에 소수 둘째 자리로 반올림한다.

코스 품질을 나타내는 별도 점수나 MMR 점수는 응답·DB에 저장되지 않는다. 세 코스는 다시 비교하거나 정렬하지 않는다.

API 계층은 추천 3개를 하나의 트랜잭션으로 다음 테이블에 저장한다.

- `trip_recommended_courses`
- `trip_course_treatments`
- `trip_daily_schedules`
- `trip_daily_schedule_places`

DB가 만든 추천 ID를 문자열로 바꿔 `course_id`에도 넣는다. 코스 선택 피드백은 로그인 사용자 본인의 추천만 허용하며 애플리케이션 수준에서 중복 저장을 피하지만, 동시 요청을 막는 DB UNIQUE 제약은 코드에 선언되어 있지 않다.

## 10. 대량 데이터 정제 규칙

### 10.1 적재 전 필수 검증

아래 조건을 통과하지 못한 행은 DB에 넣지 않는 것이 안전하다.

1. `kakaoPlaceId`가 비어 있지 않고 전체 병합 데이터에서 유일하다.
2. `placeName`이 비어 있지 않다.
3. `mapX`는 유효한 경도, `mapY`는 유효한 위도이며 서울 범위 안이다.
4. `isIndoor`, `isHeatSource`, `isMassageSpot`은 결측 없는 0/1이다.
5. `walkHard`는 결측 없는 정수 1~5다.
6. `primaryTypeName`은 승인된 고정 목록 중 하나다.
7. `categoryName`은 키워드 판정에 충분한 원본 카테고리 경로를 유지한다.
8. 주소 기반 대상 지역 판정을 통과한다.
9. `isNa=1` 행은 제외한다. 이 필드는 엔진이 읽지 않으므로 적재 전에 처리해야 한다.
10. 테마카페, 성인업소 가능 장소, 공원 부대시설 등 오탐 검수를 통과한다.

### 10.2 현재 수집기 기본값

추가 자치구 수집기(`scripts/collect_district_places.py`)는 기본적으로 다음 값을 만든다.

| 유형 | `primaryType` | `primaryTypeName` | indoor | heat | massage | walk |
|---|---|---|---:|---:|---:|---:|
| 카페 | `cafe` | `카페` | 1 | 0 | 0 | 1 |
| 드럭스토어 | `drugstore` | `드럭스토어` | 1 | 0 | 0 | 1 |
| 백화점 | `department_store` | `백화점` | 1 | 0 | 0 | 3 |
| 문화시설 | `cultural_facility` | 미술관/공연장/박물관/영화관/문화원 등 | 1 | 0 | 0 | 2 |
| 복합문화공간 | `complex_cultural_space` | `복합문화공간` | 1 | 0 | 0 | 2 |
| 찜질방·사우나 | `heat_source` | `찜질방/사우나` | 1 | 1 | 0 | 1 |
| 마사지 | `massage_spot` | `안마/스파` | 1 | 0 | 1 | 1 |
| 스파 | `spa` | `안마/스파` | 1 | 1 | 1 | 1 |
| 공원 | `park` | `공원` | 0 | 0 | 0 | 2 |

### 10.3 수집·선별 파이프라인

추가 자치구 수집 스크립트의 현재 규칙은 다음과 같다.

1. 카페는 약 0.006도 격자로 Kakao category 검색하고, 나머지는 `서울 {구} {키워드}` 검색을 한다.
2. 버퍼된 경계 상자를 쓰되 최종 소속은 `addressName`의 정확한 구 토큰으로 판정한다.
3. 필수 ID·좌표가 없으면 제거한다.
4. 유형별 deny 키워드와 카테고리 조건으로 1차 오탐을 제거한다.
5. 같은 Kakao ID는 합치고 검색 키워드만 누적한다.
6. 카페와 웰니스만 비공식 Kakao 장소 엔드포인트로 popularity를 계산한다.
7. 카페는 popularity 5, 웰니스는 4 이상만 자동 선별한다. 조회 실패는 0으로 만들지 않고 오류 상태로 남긴 뒤 제외한다.
8. 공원·웰니스·복합문화공간과 일부 테마 장소를 수동 검수한다.
9. 공원은 구별 허용 목록만 남기며, 같은 구·이름 중 전화번호가 있는 대표 행을 선호한다.
10. 최종 파일에서 ID 중복, 빈 ID, 빈 좌표, `isNa=1`, 잘못된 자치구를 검사한다.

Popularity 계산식은 다음과 같으며 half-up으로 0~5 정수화한다.

```text
blog_score = min(5, log10(blog_count + 1) * 2.5)
raw = average_score * 0.7 + blog_score * 0.3
평균 평점이 없으면 raw = blog_score
popularity = clamp(half_up(raw), 0, 5)
```

현재 생성 보고서 기준 4개 구에서 자동 선별된 1,387행 중 수동 검수 후 1,188행이 승인되었고, 최종 검증상 중복 ID·빈 좌표·`isNa=1`·잘못된 자치구는 모두 0이다.

## 11. 데이터 품질이 추천에 미치는 영향

| 데이터 문제 | 실제 영향 |
|---|---|
| `primaryTypeName` 표기 흔들림 | 목적 키워드 누락, 다양성 왜곡, 드럭스토어 중복 제한 실패, skip 설정 실패 |
| `categoryName`을 지나치게 축약 | 목적·슬롯 키워드와 상세 유형 중복 벌점이 작동하지 않음 |
| 야외를 indoor로 잘못 표기 | 제모·필링·피부레이저 등의 안전 차단이 무력화됨 |
| heat/massage 플래그 누락 | 시술 후 위험 시설이 추천될 수 있음 |
| `walkHard` 과소평가 | 고활동 BLOCK/PENALTY 누락 및 활동 점수 왜곡 |
| 좌표 반전/결측 | 정상 장소가 제거되거나 비정상 거리·코스가 생성됨 |
| Kakao ID 중복 | DB PK가 다르면 같은 실제 장소가 여러 코스에 중복될 수 있음 |
| 특정 유형 과다 수집 | min-max 정규화와 탐욕 선택 때문에 결과가 그 유형에 편향될 수 있음 |

## 12. 로직 수정 전에 확인할 지점

대량 데이터 확장과 함께 우선 검토할 위험은 다음과 같다.

1. **전체 테이블 로드**: 요청마다 모든 장소를 조회하므로 데이터가 커질수록 메모리와 Python 계산량이 선형 증가한다. 좌표 범위·지역·활성 상태를 DB 쿼리에서 먼저 제한하는 편이 필요하다.
2. **전 요청 완전 비중복**: 여행 일수가 늘면 하루 9개씩 새 장소가 필요해 쉽게 실패한다. “같은 날 비중복”과 “날짜 간 재방문 허용”을 분리할지 결정해야 한다.
3. **실제 순위 점수 부재**: rank는 생성 순서다. 비교 가능한 course score를 저장하거나 이름을 바꾸는 선택이 필요하다.
4. **정규화된 타입 계약 부재**: DB 제약이나 코드 enum이 없어 새 표기가 조용히 들어온다. `primaryTypeName` 허용 목록과 매핑 버전을 코드/적재 검증에 두는 편이 안전하다.
5. **좌표·범위 검증 부재**: 0.0 대체를 제거하고 적재 또는 요청 시 명시적으로 실패시켜야 한다.
6. **뷰티쇼핑 제외값 불일치**: YAML의 제외 카테고리와 수집기의 `안마/스파` 표기를 맞춰야 한다.
7. **재배열 후 거리 무검증**: 최종 방문 순서의 구간 거리와 총 거리 제한이 필요하다면 재검증해야 한다.
8. **Popularity 미사용**: 수집 컷에만 쓰이며 추천 랭킹에는 반영되지 않는다. 품질 신호로 사용할지는 별도 결정이 필요하다.
9. **테스트 단절**: 핵심 추천 테스트가 삭제된 과거 모듈을 import해 현재 엔진을 보호하지 못한다.
10. **설정 검증 부재**: YAML 키나 점수 매핑이 빠지면 런타임 TypeError/KeyError가 날 수 있다. 서버 시작 시 스키마 검증이 필요하다.

## 14. 유지보수 원칙

- 규칙의 수치나 키워드를 바꾸면 YAML, 이 문서, 현행 엔진 테스트를 같은 변경에서 갱신한다.
- 데이터 컬럼을 추가하기 전에 “수집용 메타데이터인지, 추천 입력인지, 응답/분석용인지”를 구분한다.
- 새 `primaryTypeName`을 추가할 때 목적 키워드, 슬롯, skip, 다양성, 시술 위험 플래그까지 함께 검토한다.
- 대량 적재 전에는 정제 결과뿐 아니라 실제 추천 시나리오별 후보 수와 하루 9개 완전 비중복 가능 여부를 검증한다.
- 과거 설계 문서는 삭제하지 않더라도 `legacy` 표시를 해 현행 실행 규칙과 혼동되지 않게 한다.
